The operator created a separate Backblaze B2 account and a private receipt bucket. ## Observed results

- Bucket `HeadBucket`: HTTP 200 using the scoped writer key.
- `GetObjectLockConfiguration`: enabled. The bucket had no default retention; the client must request and verify per-object retention.
- `GetBucketEncryption`: AES-256 default encryption.
- An S3 `PutObject` with `If-None-Match: *`, governance retention and AES-256 returned HTTP 501 `NotImplemented`. The same synthetic upload without the conditional header returned HTTP 200 and a version ID.
- `GetObjectRetention` returned governance mode and a one-day retain-until date for the uploaded synthetic version.
- A second upload of different bytes under the same retained key returned HTTP 200 and a second version. Object Lock retained the first version; it did not prevent a new latest version.
- A separately scoped recovery-reader key listed both versions and read both bytes.
- The application B2 adapter, using a fresh synthetic namespace, passed upload, same-receipt retry, independent-reader list/read, and changed-receipt conflict rejection. It verified per-version retention before returning from append.
- The maintainer approved 30 days of governance retention for synthetic and pilot pause receipts and confirmed that the separate recovery-reader key and signing secret can be held in a password manager outside Supabase and Render, accessible to another authorized operator. A fresh tiny synthetic receipt with 30-day governance retention was uploaded and read through the separate recovery key; the adapter verified the full requested retention interval.
- The maintainer later confirmed the signing secret and recovery-reader key pair were saved in that separate password manager and that a second authorized operator retrieved them.
- An opt-in live HTTP/PostgreSQL test used a dedicated disposable local database, synthetic AAL2 operator, and fresh B2 namespace with 30-day governance retention. It acknowledged a pause, accepted a same-key retry with one audit and follow-up, rebuilt a missing operation, audit, follow-up, and paused state from the B2 receipt, remained restricted, and wrote a separate B2 reopening receipt only after a manual reopening decision. The test passed. The ordinary repository suite skips this external-provider test.
- The repository `npm run check` passed with the disposable local PostgreSQL and Docker runtime test. Lint had zero errors and ten existing warnings. An earlier sandboxed attempt failed because local PostgreSQL and Docker connections returned `EPERM`; the authorized rerun passed.
