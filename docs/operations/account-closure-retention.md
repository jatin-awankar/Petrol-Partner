# Account closure and retention status (ticket 28)

`POST /v1/profile/closure-requests` records a participant's closure request and exposes a due date and processing state; `GET` on the same path returns it. Repeated requests return the same request. A request with an active pilot offer, confirmed or held allocation, open journey or settlement review, or unresolved driver incident starts held. The request does not cancel a commitment, resolve a case, disable an identity, or erase data.

An MFA-authorized, currently allowlisted operator can page through closure work and record a scoped hold with a reason and review date. Hold and release requests require idempotency keys; replay with the same key returns the same result and conflicting payloads fail. A commitment hold cannot be released while a confirmed seat or pilot offer remains active; case-scoped holds cannot be released while known journey, settlement, or incident cases remain open. Legal-review holds cannot be released through this API until an approved condition-evidence path exists. Releasing an allowed hold records the operator and reason and rechecks active commitments and cases before marking the closure pending. These controls are an inventory and safety gate; an expired review date is not automatic permission to erase evidence. The queue exposes failed-provider state for future deletion processing, but no provider deletion runner is enabled by this ticket.

Closure request, hold, and release operations commit with a stable event ID and append a signed independent receipt before success. Missing evidence leaves the operation pending and restricts protected writes; retry with the same request or idempotency key can finish acknowledgement. Global operator reconciliation replays request and hold history from the receipts before writes may reopen. Migration `0034_closure_recovery.sql` extends the event ledger without changing the committed `0033` checksum. If any pre-0034 closure events exist in a deployed database, inventory them before applying the migration and reconcile their missing independent evidence; do not claim they were previously recoverable.

These recovery receipts include stable application IDs and hold details. They are restricted operational evidence, distinct from the non-personal deletion receipts below. Their provider lifecycle and removal at account closure are still unresolved, so this implementation does not authorize production account erasure.

`GET /v1/operator/account-retention/status` returns aggregate counts for overdue closures, held and failed closure states, due or failed student and driver-car evidence objects, and non-personal deletion receipts. It also counts users older than 30 days without a currently verified student decision, ride offer, booking, allocation, or closure as **onboarding review candidates**. This includes pending and rejected verification records. This count is not a deletion instruction: provider identity, unreviewed evidence, legacy payment data, and other relationships must be inventoried before a 30-day cleanup can run. The endpoint requires current MFA and allowlist access and sets `Cache-Control: private, no-store`.

The `pilot_deletion_receipts` schema contains only a random receipt ID, completion time, policy version, and aggregate counts. No receipt is currently emitted: there is no completed deletion path. A restored older database cannot yet use these receipts to identify and suppress resurrected information. Before enabling erasure, approve an independently held deletion manifest design that can identify restored records without putting deleted personal content in the public receipt, then test restore reconciliation against an older snapshot.

The existing seven-day raw evidence worker remains in place. It requires a verified provider for real objects and retries deletion failures. This ticket does not change its deadlines. The broader 30-day unused-onboarding, 90-day pilot-end history, account-closure direct-contact, export, provider metadata, cache, and backup lifecycles need an inventory of deployed data and actual provider behavior. Do not run deletion against live accounts or represent a closure request as completed erasure. The published privacy notice and support decisions must be checked before activating the lifecycle.
