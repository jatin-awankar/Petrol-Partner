# Database backup and narrow operator recovery (ticket 11)

This procedure is for synthetic or explicitly authorized sanitized data. It is not a launch approval. Keep real trips disabled. The primary database, Auth provider, object store, and receipt store are separate failure domains.

## Prerequisites and cadence

1. Inventory the source database, migration ledger, application users, roles, extensions, object stores, deletion obligations, and deployed writers before selecting a source. Do not infer the deployed baseline from this repository.
2. Apply forward migration `0011_backup_attempts.sql` only after that inventory and a pre-change backup. Give the API runtime role `SELECT` on `pilot_backup_attempts`; give the isolated backup job identity `INSERT` and `UPDATE` on that table plus read access to source data. The backup job's role export may require a separate privileged connection; use a controlled read-only maintenance window and review the `roles.sql` output before any role restoration.
3. Install matching-version `pg_dump`, `pg_dumpall`, `pg_restore`, and `tar` on the backup and recovery hosts. Provide an independent private B2 bucket, scoped write/read keys, and an independently recoverable 32-byte encryption key. The B2 account, read key, and key backup must remain accessible when the primary database and Auth provider are down. Store no key or credential in the database, repository, or browser.
4. Configure `PILOT_BACKUP_DATABASE_URL`, `PILOT_BACKUP_B2_ENDPOINT`, `PILOT_BACKUP_B2_BUCKET`, `PILOT_BACKUP_B2_KEY_ID`, `PILOT_BACKUP_B2_KEY`, `PILOT_BACKUP_B2_PREFIX`, and base64 `PILOT_BACKUP_ENCRYPTION_KEY` in the backup runner's secret store. Give the API a separately scoped B2 read key using `PILOT_BACKUP_B2_ENDPOINT`, `PILOT_BACKUP_B2_BUCKET`, `PILOT_BACKUP_B2_KEY_ID`, and `PILOT_BACKUP_B2_KEY`; it reads the latest encrypted object and checks its version and SHA-256 before marking backup health green. If the dump role cannot read global roles, use a separately controlled `PILOT_BACKUP_GLOBALS_DATABASE_URL`. Set `PILOT_BACKUP_DATA_APPROVED=true` only for the inventoried synthetic or approved sanitized source. The API checks backup freshness in production; use `PILOT_BACKUP_REQUIRED=true` for a local rehearsal.
5. `ops/pilot-backup/render-cron.example.yaml` proposes a Docker backup runner every 20 minutes outside the API and worker processes. It is deliberately outside the active Blueprint: the maintainer authorized synthetic data only and no added cost, while Render cron jobs have a monthly minimum charge. The command holds a database advisory lock, records overlapping attempts as failures, and refuses an overlapping run. Alert on a failed or running attempt and on snapshot age above 50 minutes. The 20-minute interval leaves 30 minutes for export/upload and ten minutes before the one-hour recovery-point ceiling. Measure actual export/upload times and shorten the interval if needed. The recorded snapshot time is a conservative lower bound taken before `pg_dump` acquires its database snapshot.

The backup runner exports a PostgreSQL custom-format database dump and global roles metadata. Raw verification objects must remain in separate restricted storage; inspect the database schema and exports for embedded raw bytes before the first run. Both exports are packaged and encrypted with AES-256-GCM before upload. The runner verifies the uploaded object version by reading its full ciphertext and comparing SHA-256. It uploads decryption metadata and records the snapshot, upload time, checksum, and failed attempts in `pilot_backup_attempts`. A failed upload does not advance the completed snapshot. The operator console shows age, live object verification, and recent failed attempts. When protection is required and the latest completed snapshot is older than 50 minutes or its object cannot be verified, pause/reopen acknowledgements are refused and recovery mode is restricted. The live check reads the complete encrypted object, so measure its latency and B2 read cost before deployment. A matching ciphertext does not replace a timed restore compatibility rehearsal.

## Restore rehearsal

1. Fence old API, worker, cron, webhook, and manual writers at the deployment layer. Record the fence time and verify old credentials cannot write. Do not point a live deployment at the restore target.
2. Prepare a new, explicitly disposable local database whose name ends in `_test`, with `TEST_DATABASE_DISPOSABLE=true`. Set `DATABASE_URL` to that target and the independent B2 reader settings and encryption key. Run `node scripts/pilot-restore-rehearsal.mjs <backup-attempt-uuid>`. The command checks that the target is empty, sets its default transaction mode to read-only for new connections, then checks the object version and checksum, decrypts and authenticates it, validates dump and role-export hashes, and restores data into the disposable target. It places restored pilot recovery state in restricted mode. The role export is inspected but never automatically applied. The database default can be overridden by a privileged client and does not replace the deployment-layer fence in step 1. To check only the empty target and database default before a rehearsal, run `node scripts/pilot-restore-rehearsal.mjs --fence-only`.
3. Record complete elapsed time from incident declaration and writer fence through restore, receipt inspection, reconciliation, safe reads, and manual reopening decision. The script prints only its own restore duration. Locate pause/reopen receipts in the independent receipt store using the recovery-reader key. Compare every receipt at or after the recorded lower-bound timestamp to the restored database; this intentionally includes an overlap with the database snapshot. Use the existing `POST /v1/operator/reconcile` path under current authorized operator access to rebuild a missing acknowledged pause, audit, follow-up, and notification record. Reconciliation suppresses uncertain email jobs pending review and does not send external notifications again. Verify the restored capability state, operation ID, original operator, and timestamp. Do not reopen writes until all receipts and fallback incidents have been reviewed.
4. Validate identity mappings, capacity, commitments, journey outcomes, settlements, deletion records, and incident fallback records before any manual `/reopen` decision. A complete live cutover, provider session outage, key rotation, and four-hour safe-read target remain ticket 31 work.

For basic safe reads when the primary Auth session is unavailable, give the recovery operator a separate read-only credential to the restored target and run `RECOVERY_DATABASE_URL=... npm run recovery:status:offline`. The command begins a PostgreSQL read-only transaction and reports recovery mode, capabilities, and aggregate counts without personal contact data. The synthetic exercise used this command against the restored target. A real outage still requires separately held credentials and a vetted contact roster.

## Independent incident access and lifecycle

Maintain a printed or separately hosted contact roster for the primary database, Auth, B2, deployment, support operator, and incident lead. An operator needs a recovery-reader key and decryption key independent of the primary Auth session. The current browser console requires an Auth session and cannot serve as the outage contact store. Safe read-only service during an Auth outage needs an independently approved access path before launch.

Backup objects contain personal data. Set a finite bucket lifecycle aligned with the pilot's 90-day post-end/account-closure deletion policy, and record provider-side deletion/version behavior. A deletion request must cover active data, raw verification storage, exports, backup versions as they expire, and separately retained signed receipts; hold exceptions require a recorded unresolved case. Immutable retention must not be promised indefinitely. Inspect the bucket's actual lifecycle, object versions, and deletion receipts before calling deletion coverage complete. The synthetic `ticket11synthetic/` objects have a 31-day hide and one-day noncurrent-version deletion rule; this does not set a policy for any real-data prefix. Backblaze maps S3 expiration to hiding and noncurrent-version expiration to deletion, and locked versions cannot be deleted until retention ends. See [Backblaze's S3 lifecycle mapping](https://www.backblaze.com/apidocs/s3-put-lifecycle-configuration) and [Object Lock behavior](https://www.backblaze.com/docs/cloud-storage-object-lock).
