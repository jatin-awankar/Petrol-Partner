## Forward-only expansion design

This is a schema contract for later implementation tickets, conditional on the fresh inventory and external policy decisions. Never stamp an unknown ledger or edit an applied migration. Keep `users.id`, every existing FK, historical approval, booking, allocation, contribution, settlement and payment row unchanged. No historical corridor row receives a synthetic route or an unrestricted declaration. New rows get a distinct immutable policy family and version; a bare integer `policy_version` is insufficient because `pilot_corridor_policies.version` already begins at 1.

1. Add immutable `booking_policy_versions` keyed by `(policy_family, version)` with currency, approved rule snapshot/hash, effective time, and `approved_for_real_bookings=false` by default. Families include `pilot_corridor` and `unrestricted_route`; old corridor policy IDs remain intact. Add nullable family/version references to new use-case records, with an explicit legacy classification in the read layer for preexisting rows. Do not backfill a guessed policy version. Only backfill rows whose original `pilot_policy_id` and frozen allocation/obligation snapshots prove the corridor version; report ambiguous rows for manual decision.
2. Add a versioned posted-route table keyed by `(offer_id, route_version)`, owned through `ride_offers.driver_id`, with server-verified provider/mode, provider route reference or digest, canonical geometry, cumulative distance along that geometry, verification time, and immutable verification metadata. Keep route geometry and provider references private to the appropriate read projection. Existing offer pickup/drop fields remain historical fields. New unrestricted offers reference one verified route version; no route revision overwrites an accepted version.
3. Add a route-segment/accepted-terms table keyed by allocation or an equivalent immutable one-to-one key. It records the referenced posted-route version; ordered pickup/drop positions and safe point coordinates; server-verified segment distance in a declared integer unit; distance source and algorithm version; vehicle category; rate in paise per kilometre; rounding rule; currency; policy family/version; final integer-paise contribution; and creation/acceptance time. Pending requests retain a versioned proposed segment snapshot; acceptance copies it atomically after server revalidation. Use new nullable references on old rows, with a family-specific constraint requiring complete segment terms on **new unrestricted** accepted rows, not on historical rows.
4. Add indexes and FKs without dropping legacy structures. Use `NOT VALID` checks/FKs where PostgreSQL supports them, validate after aggregate exception checks, and use concurrent indexes outside migration transactions if needed. Enforce ordered positive segment distance, valid coordinates and positions, one frozen accepted segment per allocation, route/offer identity and version consistency, INR currency, positive paise, and unique idempotent operation keys. Database constraints cannot prove route geometry or owner policy alone: acceptance must lock the offer/route/request/seat rows, check current declarations and restrictions, validate the route segment, and commit terms, allocation, audit and notification work together. Preserve existing capacity and overlap constraints.

Old reads continue to use their original offer, booking, corridor snapshot, contribution and payment state. New reads dispatch on explicit policy family and return posted-route segment, distance source, rate, rounding and frozen amount. Audits, operator queues and recovery reports retain the family/version and route/terms IDs so a new policy never reprices or relabels old records. Historical `payment_orders`, attempts, webhooks, booking payment state, and settlements remain readable; API collection and payout boundaries stay disabled for unrestricted bookings.

## Deployment and recovery order

1. Confirm the live target, exact ledger and data aggregates; resolve divergences and record a named maintainer decision with snapshot time, exceptions, migration checksums, and approved window. Keep protected writes paused and real bookings disabled.
2. Take a provider-native backup immediately before work; record backup ID, snapshot time, encryption, retention, access permissions, and an actual restore result. Preserve independent acknowledgement receipts and provider Auth state. A restore target must be isolated and read-only until reconciliation.
3. Apply only additive migrations with a separate migration role. Deploy dual-read code that recognizes the old policy explicitly, with all new write routes and real-booking flags disabled. Run aggregate comparisons and old-client compatibility checks. Then deploy route/segment write code behind a disabled flag, validate constraints, and observe recovery/notification health. New writes require a separate launch decision after ticket 14 and the unrestricted operating/external gates.
4. If an uncommitted migration fails, roll back its transaction and keep old code. If a committed expansion fails, pause writes and roll forward with a new corrective migration; do not mutate an applied file. An application rollback is allowed only while old code reads the expanded schema and no new-format accepted actions exist. Otherwise remain in restricted mode. Restore into a separate target, reconcile newer acknowledged operation IDs, identity mappings, seats, journeys, settlements, notifications, deletions and payment history from independent evidence, then explicitly reopen writes. Never restore over newer accepted state.

Use an approved sanitized snapshot of the **verified live shape**, including representative nonzero identity, approval, vehicle, offer, booking, corridor allocation/contribution, direct-settlement and historical platform-payment states if present. Preserve ID/FK relationships while removing contact fields, provider subjects, raw evidence and payment payloads. Rehearse the exact production migration prefix and mixed-version application sequence on an isolated disposable PostgreSQL copy with separate runtime/migration roles. Compare pre/post table and status counts, primary keys, ownership relations, all FK-orphan counts, frozen terms and currency/paise totals by table/status, ledger checksums, old reads, new read routing, rollback compatibility, and backup restore/reconciliation. Verify a separately protected Auth-provider export/recovery rehearsal and reconcile restored subjects to the same application-user IDs before any write reopening. Exercise route revision, rejected off-route or reversed points, failure to verify a segment, concurrent last-seat acceptance on separate connections, retries, notification failure, and an older-snapshot restore with newer acknowledged operations. Any changed historical identity, owner, term, amount or payment fact, unexplained row difference, or ledger mismatch blocks deployment.
