This runbook prepares a synthetic release. The provider arrangement is still undecided (ticket 07). No command here authorizes provisioning, deployment, migration of a deployed database, repository protection changes, or real trips.

## Immutable artifact and configuration contract

After checks and a commit, run `npm run release:artifact -- /approved/output`. The command requires a clean tree and produces a tar archive of exactly `HEAD` and a SHA-256 sidecar. Record the commit, digest, byte count, toolchain (`node 24.20.0`, `npm 11.19.0`), CI run, migration ledger, and deployment image digest in the release record. Extract into an empty directory, run `npm ci`, `npm run runtime:check`, and `npm run check`; compare the archive hash before use. The archive contains tracked source, not installed dependencies or secrets. Build the web, API, and worker from this commit with the lockfile. Do not substitute a later branch tip.

Keep secrets in the selected provider's secret store, never in the artifact or `NEXT_PUBLIC_*`. Required groups are: database URL with TLS and least-privilege application/migration roles; exact `APP_ORIGIN`, API and web public URLs; Supabase Auth URL and server credential, callback allowlist and SMTP sender; private evidence bucket and server-only credential; independent acknowledgement receipt writer, signer, separate recovery reader, and retention; backup export/encryption credentials; worker, email, notification, and external-monitor configuration; approved corridor policy, stop/contribution table, support window/contact, and operator allowlist/MFA. `docs/operations/provider-arrangement.md`, `docs/operations/auth-cutover.md`, and API/worker `config/env.ts` define current variable names and fail-closed behavior. Record each configured value's owner and verification timestamp without exposing secret values. Do not set provider-verified flags from a synthetic test.

## Migration, reversal, and roll-forward

1. Inventory the selected deployment's schema, application users, provider subjects, identity mappings, active commitments, payment history, recovery receipts, and migration checksums. Existing data and deployed baseline are unknown until this is done. Stop if the history differs from the clean forward baseline in `docs/operations/migration-baseline.md`.
2. Take a provider-native backup and an independently readable encrypted export. Restore each to an isolated target and measure recovery time; reconcile all newer acknowledged operations before any protected writes resume. Record identifiers, times, hashes, exceptions, and operator signoff privately.
3. Run `npm run db:migrate -- --plan`, compare checksums to the reviewed release, then `--check` against staging. Rehearse application compatibility with the old and new schema on a separate synthetic copy before applying forward-only migrations to staging. Run the runner once, then `--check`, aggregate inventory and referential/identity reconciliation.
4. Deploy web, API, and worker built from the same commit. Check readiness separately for process, database, worker, backup, and protected-write permission. Verify active routes and independent recovery receipts before opening synthetic writes.
5. On a failed pre-commit migration transaction, keep the old code and investigate. After a migration commits, pause protected writes and roll forward with a corrective migration if old code is incompatible. Revert application code only after proving it reads the new schema and preserves new operations. Never reverse a migration by editing applied SQL or restoring over newer acknowledged writes.
6. Reopen writes only after restore reconciliation, current operator authorization, worker and notification recovery, and a recorded operator decision. Keep real trips disabled until all pilot launch gates have evidence.
