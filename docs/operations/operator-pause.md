# Operator pause and recovery (ticket 09)

The `/operator` browser page uses the authenticated API. Every operator endpoint checks current application role, account status, allowlist membership, the current provider session, and AAL2 MFA. `POST /v1/operator/pause` requires an `Idempotency-Key`, a capability (`offers`, `requests`, `acceptance`, or `booking`), the desired paused state, and a reason. Use a new key for each distinct decision. Look up an ambiguous result by the same key at `GET /v1/operator/operations/by-key/:key`; preserve the key until the result is known. A current operator completing another operator's pending decision can check its stable ID at `GET /v1/operator/pending/:id` before retrying.

The migration initializes all capabilities paused and recovery mode restricted. The operator must first inspect recovery evidence, call `/reconcile`, and make a recorded manual `/reopen` decision. Reopening recovery does not resume individual capabilities. The public `/v1/operator/pilot-status` endpoint reports effective pause state and recovery mode without exposing operator identities, reasons, or internal recovery causes. The authenticated `/v1/operator/status` endpoint gives authorized operators the diagnostic state. Ride and booking API guards reject paused activity, and PostgreSQL triggers serialize relevant inserts and booking mutations with pause decisions.

The pause action commits its operation, state, audit row, and follow-up row in one transaction. Reopening also requires a stable idempotency key, commits a decision and audit before writing a separate signed receipt, and only then changes recovery mode to open. A restored reopening receipt identifies the prior decision and the digest of receipts inspected at reopening, but does not reopen writes automatically. A new restore requires a fresh reconciliation and reopening decision. It writes an HMAC-signed, fsynced receipt before publishing acknowledgement. A receipt failure leaves the operation pending and restricts further activity. Reconciliation restores missing operation/audit/follow-up/state records from surviving signed receipts using original decision timestamps; it does not reopen automatically. Missing acknowledged receipts also restrict reads and return `pending_unknown` from operation lookup.

The reusable seam for later protected actions is `apps/api/src/modules/protected-mutation/protocol.ts`: operation states, the independent-evidence store contract, and a PostgreSQL transaction helper. Current operator authorization is reusable through `operator.authorization.ts`. Each later domain service must still implement its own current policy checks, business/audit/follow-up transaction, evidence contents, recovery, and crash tests; this pause slice does not certify those other mutations. The HTTP/PostgreSQL integration suite exits and restarts a separate API process at intent, commit, receipt, and acknowledgement boundaries, then retries with the same key and verifies one operation, audit and follow-up.

`PILOT_RECEIPT_SECRET` is required for pause writes and recovery actions. In development and tests, `PILOT_RECEIPT_BACKEND=file` and `PILOT_RECEIPT_PATH` use one signed, fsynced receipt file per operation; reopening uses a sibling `.reopen` directory. The file backend is rejected in production. The settings are optional at API startup so the site remains safely paused when no provider is configured.

The B2 backend requires `PILOT_RECEIPT_BACKEND=b2`, `PILOT_B2_ENDPOINT`, `PILOT_B2_BUCKET`, `PILOT_B2_WRITER_KEY_ID`, `PILOT_B2_WRITER_KEY`, `PILOT_B2_PREFIX`, `PILOT_B2_RETENTION_DAYS`, and `PILOT_RECEIPT_SECRET`. Use a private bucket in a separate Backblaze account with Object Lock and AES-256 bucket encryption. The prefix is a deployment namespace and must contain only lowercase letters, digits, hyphens, and `/`; use a fresh namespace for each environment. Keep the signing secret and a separate read/list recovery key outside the database backup. The writer key must be scoped to this bucket and permitted to upload, list versions, read versions, and read retention and bucket settings. Do not put provider keys in the repository or browser.

The B2 adapter requests governance retention and AES-256 on each object, reads the returned version's retention, then reads every version under the operation key before acknowledgement. It rejects a missing, malformed, deleted, or conflicting version. This is necessary because B2 returned HTTP 501 for S3 `If-None-Match` upload and accepted a second version of an Object-Locked key in the 2026-09-25 synthetic rehearsal. PostgreSQL row locks serialize normal publishers; version inspection detects unexpected same-key writes. An uncertain upload remains pending and restricted until retry or reconciliation identifies durable evidence. The maintainer approved 30 days of governance retention and confirmed separate password-manager custody of the recovery-reader key and signing secret, accessible to another authorized operator. A 30-day synthetic receipt was verified through the separate key. The bucket has Object Lock enabled but no default retention; launch still requires credential rotation, provider-wide outage and full restore rehearsals, deployment cutover, and verification of the deployed role configuration. The local B2 rehearsal is not evidence that those launch gates have passed.

Use `MIGRATION_DATABASE_URL` for migrations outside an explicitly disposable test database and `DATABASE_URL` for the API runtime. The migration command checks that these connect to the same database under different identities, that the migration identity can create schema objects, and that the runtime identity cannot create in `public`, own public tables, or hold superuser, role creation, database creation, or row-security bypass privileges. Only `TEST_DATABASE_DISPOSABLE=true` with a localhost database ending in `_test` permits `DATABASE_URL` alone. On the separate clean Supabase pilot project, `0007`–`0008` are applied and checksum-verified, and the new `pilot_api_runtime` role has DML access to the pause/reopen tables without schema creation or migration-ledger update rights. The original Render-connected database and deployment were not changed; restricted mode remains the safe default. See `docs/operations/evidence/ticket09-b2-2026-09-25.md`.

A pending `intent` after a process crash can be resumed by retrying its original idempotency key and payload. If the key or original actor is unavailable, a different current MFA operator can inspect the original capability, direction and reason, enter a separate review reason, and complete the pending decision through `POST /v1/operator/operations/:id/resume`. An `intent` handoff commits the original business decision, audit and follow-up with the completing actor recorded. A `committed` handoff preserves the original business audit and records who completed the evidence. The independent receipt identifies both actors and which stage was handed off. Publication holds the operation row lock while writing the receipt, so competing completion attempts cannot publish conflicting evidence. This path never opens restricted mode automatically. If a receipt already exists, reconcile it instead of handing off. Reconcile surviving receipts and make a separate manual reopening decision before allowing writes.
