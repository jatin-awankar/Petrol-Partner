# Operator pause and recovery (ticket 09)

The `/operator` browser page uses the authenticated API. Every operator endpoint checks current application role, account status, allowlist membership, the current provider session, and AAL2 MFA. `POST /v1/operator/pause` requires an `Idempotency-Key`, a capability (`offers`, `requests`, `acceptance`, or `booking`), the desired paused state, and a reason. Use a new key for each distinct decision. Look up an ambiguous result by the same key at `GET /v1/operator/operations/by-key/:key`; preserve the key until the result is known. A current operator completing another operator's pending decision can check its stable ID at `GET /v1/operator/pending/:id` before retrying.

The migration initializes all capabilities paused and recovery mode restricted. The operator must first inspect recovery evidence, call `/reconcile`, and make a recorded manual `/reopen` decision. Reopening recovery does not resume individual capabilities. The public `/v1/operator/pilot-status` endpoint reports effective pause state and recovery mode without exposing operator identities, reasons, or internal recovery causes. The authenticated `/v1/operator/status` endpoint gives authorized operators the diagnostic state. Ride and booking API guards reject paused activity, and PostgreSQL triggers serialize relevant inserts and booking mutations with pause decisions.

The pause action commits its operation, state, audit row, and follow-up row in one transaction. Reopening also requires a stable idempotency key, commits a decision and audit before writing a separate signed receipt, and only then changes recovery mode to open. A restored reopening receipt identifies the prior decision and the digest of receipts inspected at reopening, but does not reopen writes automatically. A new restore requires a fresh reconciliation and reopening decision. It writes an HMAC-signed, fsynced receipt before publishing acknowledgement. A receipt failure leaves the operation pending and restricts further activity. Reconciliation restores missing operation/audit/follow-up/state records from surviving signed receipts using original decision timestamps; it does not reopen automatically. Missing acknowledged receipts also restrict reads and return `pending_unknown` from operation lookup.

`PILOT_RECEIPT_PATH` and `PILOT_RECEIPT_SECRET` are required for pause writes and recovery actions. The path names a directory containing one signed, immutable receipt file per operation; reopening uses a sibling directory with a `.reopen` suffix. They are deliberately optional at API startup so the site remains safely paused when no evidence provider is configured. The directory must live on an operator-approved independent durable volume, and the signing secret must be recoverable separately from the database. The local file adapter proves the mechanism, but no production provider has been approved or verified for separate failure domains, encryption, immutable retention, key recovery, or restoration. Do not reopen real pilot activity on the basis of this adapter alone.

Use `MIGRATION_DATABASE_URL` for migrations outside an explicitly disposable test database and `DATABASE_URL` for the API runtime. The migration command checks that these connect to the same database under different identities, that the migration identity can create schema objects, and that the runtime identity cannot create in `public`, own public tables, or hold superuser, role creation, database creation, or row-security bypass privileges. Only `TEST_DATABASE_DISPOSABLE=true` with a localhost database ending in `_test` permits `DATABASE_URL` alone. Deployed grants and connection identities remain to be inventoried and proven before real pilot activation. The production receipt provider and deployed role grants are intentionally unconfigured for this code-only pilot; restricted mode remains the safe default.

A pending `intent` after a process crash can be resumed by retrying its original idempotency key and payload. If the key or original actor is unavailable, a different current MFA operator can inspect the original capability, direction and reason, enter a separate review reason, and complete the pending decision through `POST /v1/operator/operations/:id/resume`. An `intent` handoff commits the original business decision, audit and follow-up with the completing actor recorded. A `committed` handoff preserves the original business audit and records who completed the evidence. The independent receipt identifies both actors and which stage was handed off. Publication holds the operation row lock while writing the receipt, so competing completion attempts cannot publish conflicting evidence. This path never opens restricted mode automatically. If a receipt already exists, reconcile it instead of handing off. Reconcile surviving receipts and make a separate manual reopening decision before allowing writes.
