# Operator pause and recovery (ticket 09)

The `/operator` browser page uses the authenticated API. Every operator endpoint checks current application role, account status, allowlist membership, the current provider session, and AAL2 MFA. `POST /v1/operator/pause` requires an `Idempotency-Key`, a capability (`offers`, `requests`, `acceptance`, or `booking`), the desired paused state, and a reason. Use a new key for each distinct decision. Look up an ambiguous result by the same key at `GET /v1/operator/operations/by-key/:key`; preserve the key until the result is known.

The migration initializes all capabilities paused and recovery mode restricted. The operator must first inspect recovery evidence, call `/reconcile`, and make a recorded manual `/reopen` decision. Reopening recovery does not resume individual capabilities. The public `/v1/operator/pilot-status` endpoint reports effective pause state without exposing operator identities or reasons. Ride and booking API guards reject paused activity, and PostgreSQL triggers serialize relevant inserts and booking mutations with pause decisions.

The pause action commits its operation, state, audit row, and follow-up row in one transaction. It writes an HMAC-signed, fsynced receipt before publishing acknowledgement. A receipt failure leaves the operation pending and restricts further activity. Reconciliation restores missing operation/audit/follow-up/state records from surviving signed receipts using original decision timestamps; it does not reopen automatically. Missing acknowledged receipts also restrict reads and return `pending_unknown` from operation lookup.

`PILOT_RECEIPT_PATH` and `PILOT_RECEIPT_SECRET` are required for pause writes and recovery actions. They are deliberately optional at API startup so the site remains safely paused when no evidence provider is configured. The file must live on an operator-approved independent durable volume, and the signing secret must be recoverable separately from the database. The local file adapter proves the mechanism, but no production provider has been approved or verified for separate failure domains, atomic append, encryption, immutable retention, key recovery, or restoration. Do not reopen real pilot activity on the basis of this adapter alone.

Use a separate migration database identity with schema DDL rights and an application identity limited to required table reads/writes and function execution. The runtime identity must not own the schema, create objects, bypass row security, or modify the protected pause/recovery tables outside the API's domain operations. The current repository still accepts one `DATABASE_URL` for both processes; deployed role grants and connection identities remain to be inventoried and proven before declaring this ticket resolved.

A pending `intent` after a process crash can be resumed by retrying its original idempotency key and payload. A `committed` decision can be acknowledged by retry once the evidence store is healthy. If the key or original actor is unavailable, remain restricted and preserve the pending operation for manual reconciliation; there is no safe automatic abandonment path yet.
